SID import (.sid -> .sng): files, build, tests
=============================================

Files (all plain C, no UI, depend only on gcommon.h + each other)
-----------------------------------------------------------------

gsngwrite.c/.h   GTS5 .sng writer (SNGDATA struct + sngwrite()). Used by the
                 MIDI import (gmidifile.c) and the SID import.
cpu6502.c/.h     6502 emulation, ported from SIDDump by Lasse Oorni et al.
                 (BSD license, kept in cpu6502.c). Reentrant (CPU6502 struct).
gsidimport.c/.h  The SID import: sidinfo_read(), sid2sng(), sid2sng_defaults().
sid2sng.c        Command line tool (like midi2sng).
tests/sid2sng/   Round trip test: packer harness built from the unmodified
                 greloc.c (no SDL), scripts, .sng dump/compare tools.

gmidifile.c now writes through gsngwrite.c (same output byte for byte), so
everything that links gmidifile.o also needs gsngwrite.o.


API (gsidimport.h)
------------------

  void sid2sng_defaults(SID2SNG_OPTIONS *opt);
  int sidinfo_read(const char *sidpath, SIDINFO *info);
  int sid2sng(const char *sidpath, const char *sngpath,
              const SID2SNG_OPTIONS *opt, char *report, int reportsize);
  int sid2sng_play(const char *sidpath, const char *sngpath,
                   const SID2SNG_OPTIONS *opt, SID2SNG_PLAYBACK *playback,
                   char *report, int reportsize);

SID2SNG_OPTIONS: mode (SID2SNG_AUTO/EXACT/APPROX), subtune (0 = all, up to 32),
seconds (180), rowsperbeat (0 = auto), tempo (0 = auto), patternlength (64),
loops (1 = end each subtune where it starts over and loop back).
SIDINFO: title, author, released, rsid, version, songs, startsong, clock
(0 unknown/1 PAL/2 NTSC/3 both), model (0/1 6581/2 8580/3 both), load/init/
play address, data size, speed flags.

sid2sng() returns 1/0; report gets e.g. "Exact: GoatTracker 2 song, 4
subtunes, 41 patterns, 13 instruments" or "Approximate: 11 subtunes, 3845
notes, 59 instruments, tempo 4-16, 84 patterns, 2 loop where they repeat,
..." or the error. How the song is to be played is not in the .sng: the
editor settings speed multiplier, NTSC, hardrestart ADSR, player
optimizations and tuning. sid2sng_play() gives them in SID2SNG_PLAYBACK
(multiplier 1-16, 0 = 25Hz, -1 = none fits; ntsc; adparam, -1 = not known;
optimizepulse/optimizerealtime; basepitch, 0 = the standard frequency
table, -1 = not known) and the report mentions them ("2x speed", "25Hz",
"NTSC", "hardrestart ADSR 0000", "tuned to A-4 = 423.87 Hz"). After a
successful conversion load the .sng with loadsong() and set editorInfo
.multiplier/ntsc/adparam/optimize*, and setbasepitch() (goattrk2.c; the
tracker's SID import does, then do_sound_init()). The tuning is
GoatTracker's existing base pitch setting (config "Base pitch of A-4",
gt2reloc -G, the harness -G): A-4 in Hz on the PAL clock, 12 notes an
octave; the packer writes the table it makes. APPROX finds the one the
tune's notes fit (see below); EXACT reads it back from the packed table.

APPROX speed: a player that runs at a rate GoatTracker can't (a CIA timer
that isn't a whole multiple of the frame rate, e.g. Ultima IV's 34.7 Hz, or
a 60 Hz timer on PAL) can't be played as recorded. The song keeps its rows
(and loops); choosespeed() tries PAL/NTSC x 25Hz/1-16x and takes the one
with the least: worst tempo error over the subtunes, plus 0.1 x how much
faster/slower the instruments' programs run (log2), plus 0.06 x how far the
notes are from the frequency table on that clock. Each subtune then gets the
tempo, or a funktempo pair (speedtable row, half-step averages), whose rows
last as long as the source's (fittempo()); glide speeds are scaled the same.
On the other PAL/NTSC the notes are analysed again for that clock. Gate
timers are kept below each instrument's fastest tempo (the player stops the
song otherwise). Whole-multiple rates keep the old path (same output).
Resampling the registers onto GoatTracker's ticks instead was tried: timing
exact in ticks, but source rows aren't whole ticks long, so notes land
unevenly on rows, and the resampled recording never repeats exactly (no
loops: Ultima IV went from 13 looping subtunes to none, 8 cut short).
Results: Ultima IV 1x PAL, rows/s within 3.8% for all 13 subtunes (it was
73% fast at 1x NTSC), on pitch (its table is for NTSC: on the PAL table at
the NTSC clock it is 0.35 semitones off); dojo with a 60 Hz CIA timer on PAL
1x NTSC within 0.2%; the app plays the Ultima IV import at the computed
5.88 rows/s.

The importer allocates its big buffers (SNGDATA ~140K, CPU6502 64K, the
register recording up to a few MB) on the heap and frees them; it keeps no
state between calls except one static double (the clock for pitch math), so
don't call it from two threads at once.


Building
--------

gcc / clang (Linux, macOS, MinGW), in src/src:

  cc -O2 -o sid2sng sid2sng.c gsidimport.c gsngwrite.c cpu6502.c -lm
  cc -O2 -o midi2sng midi2sng.c gmidifile.c gsngwrite.c

MSVC (Developer Command Prompt), in src/src:

  cl /nologo /O2 /D_CRT_SECURE_NO_WARNINGS /Fesid2sng.exe sid2sng.c gsidimport.c gsngwrite.c cpu6502.c
  cl /nologo /O2 /D_CRT_SECURE_NO_WARNINGS /Femidi2sng.exe midi2sng.c gmidifile.c gsngwrite.c

(gsidimport.c uses <math.h>: link with -lm where that is separate.)

Lines for makefile.common:

  - add to EXE:
        $(PREFIX)sid2sng$(SUFFIX)
  - goattrk2 target: add  gsidimport.o gsngwrite.o cpu6502.o  (next to
    gmidifile.o; gsngwrite.o is needed by gmidifile.o now)
  - midi2sng target becomes:
        $(PREFIX)midi2sng$(SUFFIX): midi2sng.o gmidifile.o gsngwrite.o
        	$(CC) -o $@ $^
        	strip $@
  - new target:
        $(PREFIX)sid2sng$(SUFFIX): sid2sng.o gsidimport.o gsngwrite.o cpu6502.o
        	$(CC) -o $@ $^ -lm
        	strip $@

(goattrk2 links with $(CXX) and libm already comes with it; add -lm to
LIBS if a platform needs it.)


Tests
-----

  sh tests/sid2sng/build.sh            # relocharness + sid2sng into tests/sid2sng/build
  sh tests/sid2sng/roundtrip.sh        # needs python3 (PY=python to change)

roundtrip.sh packs every examples/*.sng with 33 sets of packer options
(buffered, ZP ghostregs, sound FX, volume, author info, no optimization, full
buffering, multispeed 0/2/3/4x, NTSC, alternative player (-AF000), pulse/
realtime optimization off, other player/zeropage/SID addresses...), imports
each SID with sid2sng -exact, packs the result again with the same options
and compares the two SIDs byte for byte. For 5 option sets it also compares
the imported .sng with the original structurally (tests/sid2sng/sngcmp.py:
orderlists, every pattern row, instruments, wave/pulse/filter/speed table
programs, with the packer's renumbering mapped out).

Why a harness and not gt2reloc: gt2reloc links bme/resid (SDL). Also, in
this tree gt2reloc.c parses its options into globals (multiplier, adparam,
ntsc, optimizepulse...) that greloc.c doesn't read any more (it reads
editorInfo), so the real gt2reloc packs with those at 0 (25Hz speed code,
hardrestart ADSR $0000); and its -I option falls through into -J. The
harness (tests/sid2sng/harness.c) sets editorInfo from the options.

Results on Windows with MSVC 19.44 (VS 2022 Build Tools), 2026-11-10:
  - roundtrip: 14 examples x 30+ option sets, all byte-identical repacks;
    all structural compares the same
  - midi2sng before/after the writer move: same .sng bytes and report for
    7 generated MIDI files x 4 option sets
  - clang (clang-tidy front end) -std=gnu99 -Wall -Wextra: no warnings in
    gsidimport.c gsngwrite.c cpu6502.c sid2sng.c gmidifile.c midi2sng.c
  - gcc wasn't available here: build.sh (cc) isn't run yet on this machine

What EXACT can't give back (the packer drops it): instrument names, unused
patterns/instruments/table rows, instrument/pattern/table numbering
(instruments come hardrestart / no-hardrestart / legato ordered), repeated
instrument numbers in a pattern, R0 (repeat 16) orderlist commands, set-
mastervolume timing marks (without author info), the low nybble of filter
"set" rows, wavetable silent waveform $E0 without wave delays (becomes $00:
the same in the player). The editor-only settings (speed multiplier, NTSC,
hardrestart ADSR) come in SID2SNG_PLAYBACK and the report. A tempo other than the default comes
back as instrument $3F's AD (the tracker's "tempo instrument" convention).

APPROX smoke test (sid2sng -approx on the 14 packed examples and
examples/sid/*.sid): all convert in ~0.1-0.2 s, all results pack without
errors. Quality, measured as notes (voice, pitch, onset within half a row)
of the original that the approx song played back has: 95-100% for
dojo, transylvanian, tempo2test, wavecmdtest, consultant, everlasting;
~80-90% for cabrinigreen, ghosttrackers, unleash, Rambo, Ultima IV;
50-75% for sixpack, Beyond, hyperspace, funktest, sanction (funk tempo,
channel tempos and lots of slides, which a fixed tempo grid & instrument
programs only approximate).

APPROX instruments (2026-11-11, from examples/sid/diff, Rob Hubbard's
Commando): his players keep the gate on for one frame and play the sound
(noise burst, octave arpeggio) in the release, and their pulse sweeps pause
on each note's first frame. The importer used to see every note as a new
sound, ran out of instruments and fell back to merging them with any ADSR
(74% of the notes got the wrong AD/SR, start pulse rounded to $800). Now:
  - a pulse sweep that pauses or turns around on the first frame goes on
    (no pulse program for the note)
  - gate off before the next row: the wave program turns the gate off and
    goes on while the release is heard (linear model of the SID release
    times); no keyoff for those notes. Tied notes' programs also stop when
    the release has died down (the hardrestart gap is silent)
  - noise rows follow the note in a tone or at the note's pitch/octaves,
    else they are absolute (fixed-pitch drums)
  - detail levels: pulse first, then program length, ADSR last; AD and SR
    never both different from the note (one command sets the other); the
    start pulse is rounded to $100 at most; identical programs count once
    against the 255 table rows; out of instruments, the most alike by ADSR
Measured by emulating the original and the packed result and comparing the
registers note by note (ADSR at the attack, waveform+gate over the audible
frames, pulse): Commando subtune 1 ADSR 10-40% -> 100%, waveforms 0-51% ->
100% per voice; subtune 2 (all 11 imported) ADSR 0-33% -> 100%, waveforms
with gate 0-66% -> 100%; Ghosts'n Goblins subtune 2 ADSR 40/84% -> 100%;
Rambo subtune 1, Ultima IV, Hypa-Ball unchanged. EXACT round trip: 462
byte-identical repacks, 70 structurally same, 0 failures.
Building the harness with llvm-mingw clang needs -U__WIN32__ (greloc.c
otherwise expects gt2reloc's STDOUT/STDERR variables).

APPROX gate lengths (same day; Hypa-Ball, Ghosts'n Goblins): sustained notes
released 2-3 frames early. The player reads the next row (a keyoff, or the
next note with its hardrestart) the current instrument's gatetimer of ticks
before the row, and the importer used to put the keyoff on the row where
the gate went off, with gatetimer 2, and took a note's gatetimer from the
gap before it (in the player it times the note's own gate-off). Now:
  - the gatetimer bits are split: $80/$40 (no hardrestart / legato) from
    how the note starts, the timer from when its own gate goes off (through
    the legato notes that follow it). The gate stays on as many ticks as in
    the recording, counted from the start of the note's row (where the
    player turns it on with the first waveform); the timer picks the tick
    within the row, the keyoff (or the next note's row) the row. A gate
    going off on a row's start comes 1 tick early (the timer is 1 to
    tempo-1). Converted to the song's ticks when the speed is fitted
  - the keyoff row is chosen with the instrument's actual gatetimer; a
    tied note whose next note is off the grid gets a keyoff when the next
    row is too far for a gatetimer
  - short-gate programs count the player's first-wave frame (gate on there)
  - detail levels: exact gate timing at the first two, +-1 tick for three,
    then any (before the wave programs get shorter)
Gate length from the gate-on edge, original vs packed result, notes whose
gate goes off before the next one: Commando subtune 1 43/0/75% exact ->
100/100/100%, subtune 2 (all imported) 0/0/0% -> 100% exact; Hypa-Ball
33/73/75% within 1 tick -> 100% (all 1 tick: gates ending on a row's start);
Ghosts'n Goblins subtune 2 0/13/0% within 1 -> 100%; Rambo subtune 1
22/5/20% -> 100/99/100% within 1 (voice 0 100% exact). ADSR and waveforms
unchanged, the same detail levels as before (Rambo with all 23 subtunes is
at the lowest either way; it doesn't pack yet: "pattern too complex").
EXACT round trip unchanged.

APPROX fixes (2026-11-11, from a test set of 64 game tunes, their exports
from the tracker and screenshots of the failures). Checked by playing each
original and its packed export on the importer's emulated C64 and matching
the notes per voice (pitch, onset within 30 ms) over 40 s of every subtune:
  - Silent songs and subtunes (James Pond II, Roland's Ratrace, Yie Ar Kung
    Fu; 8 of Ultima V's 15 subtunes, 3 of Defender of the Crown's): the
    players start each channel on instrument 1 at the default tempo and
    read the rows up to the channel's first note with its gatetimer; one
    longer than a row is never reached (the packed SID's player never reads
    a row, the tracker stops the song). The packer numbers the instruments
    hardrestart / no-HR / legato first, so the first used instrument of the
    first kind becomes its instrument 1: that one is now instrument 1 in the
    song too, one whose gatetimer fits the default tempo and every
    subtune's (or its gatetimer is shortened). 49 silent subtunes -> 0.
  - "PATTERN xx IS TOO COMPLEX (OVER 256 BYTES PACKED)" when exporting
    (Gauntlet III, Green Beret, Katakis, Last Ninja, Rainbow Islands, Rambo,
    Rocket Ranger, Speedball, Yie Ar Kung Fu II): a song needing too many
    patterns gets 128-row ones, and busy ones pack to more than the
    player's 256 bytes. Their packed size is worked out as packpattern()
    does and too big ones are cut in two (64 rows always fit).
  - RSID tunes were refused. They now run on the C64 (recordfull()): init,
    which may not return (a main program), CIA 1/2 timers with IRQ/NMI, the
    VIC-II raster interrupt, the KERNAL's interrupt entry and exit
    ($EA31/$EA81/$FEBC, other KERNAL calls return). A 5 s run finds the
    interrupt source that writes the SID's voice/filter registers most (a
    CIA timer, a raster line, or the main program: then once a frame), then
    the SID is recorded at the end of each of its interrupts, at their rate.
    A main program waiting in a loop (the same CPU state again, nothing
    written but the stack, no changing I/O read) skips to the next event.
    Arkanoid, Beach Head II, Dark Castle, Great Giana Sisters, Master of the
    Lamps import; subtunes of digitized speech (Beach Head II 2-12, Dark
    Castle 2-4: samples through $D418 from an NMI or the main program)
    come out empty. Slowest: Arkanoid's 20 subtunes, ~5 s.
  - OSC3/ENV3 read as a constant: voice 3's oscillator (accumulator, noise
    shift register) and envelope now run, ported from reSID 0.16 (the
    engine in resid/, the same as https://github.com/simonowen/resid:
    WaveformGenerator::clock/writeCONTROL_REG, EnvelopeGenerator::clock &
    its rate/sustain tables), clocked by the CPU's cycles; reads come from
    the addressing mode of the instruction about to run (memaccess()).
    Paradroid, Hypa-Ball, Mutants and Master of the Lamps read them.
  - Voice 3 switched off ($D418 bit 7, not filtered, not voice 1's ring/
    sync source) is left out: GoatTracker can't switch it off, and
    Paradroid's random-number voice (noise, gate on, SR $FF) played as a
    loud constant hiss. Karateka also switches it off at times.
  - Subtunes that stop (jingles, sound effects) started over every pattern
    or so (Commando's: 12-16 notes for 2, 368 for 46); they end on empty
    rows now. The last keyoff of a tune that doesn't loop was lost.
  - Notes with pulse width 0 (silent): a pulse "going on" from before the
    voice's first pulse note, and small start pulses rounded down to 0.
  - The hardrestart ADSR was left at the editor's last setting (an earlier
    EXACT import could leave $0000). APPROX now gives the one the tune has
    in the gap before notes that start with a hardrestart (most common),
    $0F00 if none.

APPROX, the four open points (2026-11-12). Measured as before (regcmp.py
over all 64 tunes, up to 8 subtunes each, 60 s, 119068 notes; batch logs
for the rest), the tree before -> after:
  notes matched 91.7% -> 95.3%, at the right pitch 87.0% -> 93.3% (a
  semitone off 6127 -> 1430), frames at the right pitch 81.6% -> 84.3%,
  their pitch 21.7 -> 3.9 cents off on average; AD/SR differences 996/563
  -> 461/459, gate length 16249 -> 8324, pulse 33721 -> 29242 (silent
  214 -> 78), vibrato missing 2835 -> 2257 of 3376, slides missing 6925 ->
  5817 of 10796, filter cutoff 63.9% -> 77.9% of the frames; subtunes cut
  short 63 (11 tunes) -> 22 (4 tunes); notes left out as too close 12729 ->
  3821; tunes at a simplified level 43 -> 31. EXACT round trip unchanged
  (462 byte-identical, 70 same, 0 failures); 64 of 64 import and pack.
  - Tuning: the notes' pitch beyond the nearest note, as they sound, is
    averaged on a circle (tuneconsistent()); when they agree (resultant
    >= 0.5) and the base pitch that fits is 0.1 semitone or more off
    GoatTracker's table, the song gets it (findtuning(); notes again on
    that table, settuning() as calculatefreqtable()). An NTSC tune for its
    60 Hz C64 played in NTSC mode gets 423.87 Hz; many PAL tunes are ~0.35
    semitone sharp (Ghosts'n Goblins, Bomb Jack 449 Hz) or flat. 35 of 64
    get one. The speed choice no longer weighs pitch then. EXACT finds the
    packed table ("lda lo-FIRSTNOTE,y; sta; lda hi-FIRSTNOTE,y" just before
    the song table) and the base pitch that gives it (all 64 exports read
    back right). The tracker: setbasepitch() (goattrk2.c) restores the
    standard table for 0; the modern interface's control bar shows a base
    pitch (A423.9), a click goes back to the standard table. The retro
    interface only says it in the import message.
  - Instruments: a note may share an instrument that differs in one thing
    a command on its row sets: AD (5), SR (6), its own wave program (8,
    set wavepointer; both players start the instrument and then take it)
    or pulse program (9). Tried at each level after the plain match;
    programs counted once against the tables (APROGS). Silent frames (no
    waveform, test bit) keep the pitch (no note per program); noise off
    the note's octaves is a fixed pitch also in tonal notes (drum attacks:
    R-Type, Hollywood Poker Pro went from 1294 to 871 instruments needed at
    full detail). A note ended by a keyoff whose sound still changes in the
    release (an arpeggio going on) has it in its program, left out at a
    level when it doesn't fit. A slide cut to fewer frames holds its last
    tone pitch (an arpeggio coming back: the note), not the next frame's
    (a semitone off). Hollywood Poker Pro: level 10 -> 9; its slides are
    still lost (they need 4-row programs: ~200 different ones, the 255-row
    wavetable holds ~50).
  - Filter: filtertable programs that set the type/resonance/routing and
    cutoff, then modulation steps (runs of the same change per frame),
    looping when the steps repeat (the loop giving the most frames wins),
    ending where the cutoff holds (a sweep that comes again is the same
    program). Emulated frame by frame (fstep(), as gplay.c); a program is
    started (Axx, in a channel with room) on a row where the running one
    gives a cutoff more than 3 off, or other routing/type/resonance, and
    on the loop's first row. At another speed the frames are resampled to
    the song's. Table full: the cutoff (Cxx). Beyond 49% -> 99% of its
    filter frames, Krakout 8% -> 100%, Last Ninja 44% -> 92%, Hollywood
    Poker Pro 48% -> 80%. Low still: Katakis (cut-short subtunes), Yie Ar
    Kung Fu II and Master of the Lamps (fitted speeds).
  - Patterns: each channel is cut on its own into blocks (the song before
    the loop and the loop each from their start), the same block also
    when transposed (orderlist transpose -16..+14, set again at the loop's
    start) one pattern; then patterns that always follow each other are
    joined (both always together first: fewer patterns; then one of them:
    fewer orderlist positions), repeats as orderlist repeats. Blocks of
    64, 32, 16, 8 rows joined up to 64, then 128..8 up to 128: the first
    that fits, else the fewest patterns and the longest subtune (or the
    one with an orderlist over 254) cut, as before.
  - Rows: a coarser row is taken unless it loses 1% more notes (two on a
    row) than the finest, or has 5% more off its rows (before: 80% on
    them). The tune's timing shifting a frame or two against the rows now
    and then (Ultima V: a frame more every ~40 s; 177 of 570 subtunes had
    no grid with 80% of their notes) is followed (finddrift(): 4 onsets in
    a row off by the same 1-2 ticks): song ticks leave those frames out
    (or double them), rows are on song ticks (warptick()/unwarptick()), the
    loop is found with any period in the recording's ticks and whole rows
    in the song's. Ultima V: tempo 3 -> 6, notes matched 78% -> 93%, frames
    at the right pitch 55% -> 84%, 13 -> 6 subtunes cut short; Ultima IV
    74% -> 93%, Booga-Boo 61% -> 100%. Worse: Rambo 98% -> 91% (subtune 1
    gets rows twice as long).
  - Import time: a tune that gets a base pitch or the other PAL/NTSC is
    recorded twice (Ultima V 2.7 -> 4.5 s, Defender of the Crown 3.5 ->
    7.1 s; Katakis, the slowest, 10.6 -> 11.7 s).
Still open: Hollywood Poker Pro's arpeggios/slides (wavetable room);
Katakis (7 subtunes), Last Ninja (8), Ultima V (6), Defender of the Crown
